# Social notification delivery

Apply the social-profile and follower-push migrations before deploying `follower-notifications`. The app never contains a server credential or sends push messages directly.

`202610280004_post_notifications.sql` extends the same worker and schedule to comments, likes and first-time publications from accepted followed accounts. Deploy the updated worker before this migration; it accepts both the original and extended job shape. No additional schedule or secret is needed. Per-account `notification_preferences` independently controls inbox and phone delivery; new-post phone delivery defaults off. Before sending pending messages, the database rechecks preferences, current source availability, recipient access and read status. Push payloads contain a notification ID, never comment text, routes or location; the app resolves that ID through a recipient-only RPC and reads the source through RLS again. Do not backfill events from old posts or resend existing events when preferences change.

The worker deliberately uses its own server-only bearer secret: set the same randomly generated `VYRO_PUSH_WORKER_SECRET` in Edge Function secrets and Vault as `vyro_push_worker`. Deploy the function using the checked-in configuration, then run `schedule-follower-push.sql` with the project's administrative connection. The schedule requires Supabase Cron (`pg_cron`) and Vault; it enables `pg_net` when absent. Do not put the secret in SQL checked into Git, logs or client environment variables. Rotate both stored copies together. `EXPO_ACCESS_TOKEN` is only needed if enhanced push security is enabled in the Expo project.

In EAS, configure the Apple push key for the main iPhone target, enable Push Notifications and regenerate its provisioning profile. Install a new signed build after adding `expo-notifications`. Each user explicitly opts in under Sosiale varsler; an active Auth session is required when registering an installation. Tokens are not readable by clients. Sign-out disables the installation, and queued delivery checks whether the bound Auth session still exists.

The minute schedule claims pending jobs in batches of 50, with two-minute leases. Expo tickets are persisted before receipt checks; accepted tickets are never intentionally resent. Network failures retry up to five times. A lost network acknowledgement or process crash can still produce a duplicate delivery; this is at-least-once delivery, not an exactly-once guarantee. Jobs expire after 24 hours; inactive devices stop receiving notifications after 30 days. Receipts only confirm delivery to Apple's service, not display on the phone. Focus mode and the user's iOS settings may suppress presentation.

Review aggregate pending/failed job counts and sanitized error codes; do not print device tokens or authorization headers. The initial deployment on 28 October passed unauthorized (401) and authorized idle (200, zero jobs) checks. Physical delivery must still be tested from a second account with the app closed. See `docs/testing.md` for acceptance steps.
